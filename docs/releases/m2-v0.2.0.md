# M2 v0.2.0 — protected native processes

Codename: Engine OS now runs real ring-3 native verification programs in private address spaces. A new UEFI ISO is provided for VM testing; there is still no installer, shell or existing Windows application support.

## What is included

- Private CR3 contexts, shared immutable code, private zeroed data/stacks, NX and read-only mappings.
- Upper-half guarded kernel-entry stack, checked native interrupt gateway and isolated user faults.
- Generation/type/rights-checked handles, explicit reduced-right transfer, bounded IPC and shared memory.
- Repeated process/object cleanup, quotas, separate managed/boot memory accounting and CPU HLT at idle.
- English current documentation in dedicated architecture/roadmap/milestone/release folders, with tests organized per milestone and build/VM tools separated.

The normal image runs 13 initial roles plus 32 fresh survivor starts: 45 process starts, 35 clean exits and ten contained failures. It demonstrates private sentinels, IPC, mapping rights, stale handles, quotas and invalid pointer/return checks. Unconfigured SYSCALL/SYSENTER entry is sealed and tested. After completion the visible result screen remains while the CPU halts.

## Resource scope and tests

Automated QEMU/OVMF tests cover optical ISO, actual USB-device emulation, 64 MiB and 2 GiB guests, stale-mapkey retry, genuine kernel panic and malformed boot inputs. The allocator only manages conventional RAM below 1 GiB; the larger guest test is a boot/address-layout check, not full use of all installed memory.

Qualification ceilings for this finite native workload: managed peak <=512 KiB, retained managed <=64 KiB, separately retained boot resources <=1 MiB, combined managed peak+boot <=2 MiB. The final sample is 448 KiB managed peak, 60 KiB retained managed and 420 KiB boot allocations, with actual HLT observed. Exact observations and the short host-QEMU CPU interval are published in the evidence. Guest RAM is not kernel footprint; firmware/device/framebuffer and host memory are separate. This is not a usable-desktop, power or game benchmark.

## Try in VMware

Use a 64-bit UEFI VM, Secure Boot off, the new `EngineOS-M2.iso` attached/connected at power on, initially one vCPU and 128 MiB RAM. Boot the EFI CD/DVD entry. The earlier FreeBSD 15 64-bit VMware profile successfully booted M1; the label does not provide a FreeBSD kernel. M2 is supplied for the user's new VMware test, not claimed fully VMware-qualified in advance.

Download the ISO and verify it against `M2-SHA256SUMS.txt`. The release also supplies GPT-USB, kernel ELF/map, separate native user ELF and `m2-build-manifest.json`. Place downloads under `dist/` in the source checkout.

```powershell
python tools/vm/run.py
```

To build/test from source:

```powershell
python tools/build/m2.py
python tests/m2/verify.py
```

## Limits

One active CPU and cooperative trusted native programs only; no timer preemption, general threads/VM/pressure, arbitrary application loading, storage driver, installer or Windows APIs. A non-yielding arbitrary program is not yet starvation-contained. Native user mappings begin above 4 GiB; future 32-bit guest profiles need a suitable later layout. Windows 95–11 compatibility remains an explicit staged requirement, not a property of this release. M3 addresses scheduling/memory/concurrency; M4/M5 provide storage/input and installation.

Original runtime/source is MIT. QEMU/OVMF and host-only pycdlib/Pillow are separate tools with their own licensing; they are not bundled into the OS image. Historical M1 artifacts/tags remain unchanged.

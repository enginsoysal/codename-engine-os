# Engine OS 0.9.2 — automatic writable storage and reachable desktop windows

M9.2 removes the SATA-only installation gate. Engine OS automatically binds its own supported IDE, SATA, SCSI and NVMe controller implementations and uses real read/write/flush capabilities. The ordinary graphical installer, Disk tools and persistent desktop share this path. No guest driver installer is needed.

Qualification is **M92-STORAGE-VM-v1**, governed by the [exact-artifact acceptance report](../../evidence/M9.2/acceptance-results.json). The wider M9 hardware program remains in progress. A failed QEMU/OVMF SAS multi-disk restart is explicitly retained as unqualified evidence; this release does not claim universal hardware operation.

## VMware controller qualification

Every passing row includes actual graphical installation, retained-ISO restart, persisted folder creation, independent byte verification and two unforced disk-only boots using the same owned VM/NVRAM. Ethernet and sound remain enabled; DHCP must complete.

| Controller | BIOS | UEFI |
|---|---|---|
| SATA/AHCI | Qualified | Qualified |
| IDE / ATA PIO | Qualified | Qualified |
| LSI Logic parallel SCSI | Qualified | Qualified |
| LSI SAS 1068 | Qualified | Qualified |
| VMware PVSCSI | Qualified | Qualified |
| NVMe | Qualified | Qualified |
| BusLogic SCSI | Qualified with compatible device preset | Not qualified |

BusLogic uses VMware's `freebsd` device preset because VMware refuses BusLogic under `freebsd-64`. This is a hypervisor device-availability setting; the Engine OS kernel remains native x86-64. The tests do not claim that a guest driver can override a device VMware refuses to present.

Additional QEMU proof covers real modern VirtIO Block writes/flush and the original Windows-app journey, NVMe at an actual 3840x2160 framebuffer, IDE with 64 MiB RAM and one CPU, disk-utility operations and injected failures. These task reports have their own firmware/topology limits; they do not qualify every QEMU disk-only startup route.

## Desktop and resource checks

Files windows can overlap the side and bottom edges while keeping a reachable caption. Signed clipping protects framebuffer addressing. The movement test compares the complete desktop viewport against an independent full repaint after moves out and back at 100%, 150% and 200% display scale, including actual 4K. It excludes the taskbar clock from the pixel comparison.

Dragging retains no additional managed pages and idle stops repainting with both processors halted. Observed managed ownership is 4,288,512 bytes at 1280x800 and 33,370,112 bytes at 3840x2160. These counters exclude other boot-reserved/static memory; they are not total system RAM. QEMU TCG captures prove correctness, not smooth 4K monitor frame rates or 3D acceleration.

The exact starter services observed hardware keyboard IRQs during protected application execution and also installs, runs, archives/extracts with, removes and reinstalls the original 7-Zip console profile. Independent inspection checks all 106 original payload hashes and the archived/extracted document bytes. General Windows GUI/MSI and DOS compatibility remain separate work.

## Safety and open limits

- Installation still replaces the selected whole disk, with explicit consent for existing data. The native layout requires 512-byte logical sectors and its documented capacity range; 4Kn installation, RAID and dual-boot partition installation are not qualified.
- Native IDE and mixed SATA/SAS disk-management tests check FAT32/native format, partition delete/create and complete preservation of the unselected equal-capacity disk. VMware separately qualifies SAS startup.
- QEMU PVSCSI reports zero transferred bytes for the tested successful inquiry. Engine OS refuses the inconsistent completion instead of granting writable admission. VMware PVSCSI is separately qualified.
- Two QEMU/OVMF LSI SAS multi-disk restart topologies return to setup after native installation; root cause remains undiagnosed. [Recorded target-1 failure](../../evidence/M9.2/known-issues/scsi-target1-ovmf/results.json) and [mixed-controller failure](../../evidence/M9.2/known-issues/scsi-target0-mixed-ovmf/results.json). They are not passing startup gates.
- Physical controllers, arbitrary SCSI HBAs/LUNs, all GPUs, Wi-Fi/Bluetooth, hotplug, runtime display changes, multiple monitors, 3D and ARM remain separate qualification work. Secure Boot stays off for unsigned public development media.

## Reproduction

Build in an isolated checkout of the compiled code commit with the pinned tools: `python tools/build/m92.py`. Create the blank-disk package with `python tools/release/vmware_starter92.py`. The qualification harnesses use disposable owned VM images only.

Run `python tests/m92/matrix.py` for the sequential VMware matrix and exact starter; `python tests/m92/replacement.py --controller ide` and `--controller mptsas` for disk isolation; `python tests/m92/safety.py --controller ide` and `--controller mptsas` for cancellation/error handling. Run `python tests/m92/motion_native.py --resolution 3840x2160 --frames 8` for native clipping/repaint proof. The acceptance report records every gate, exact artifact and final harness hash. Never rebuild media or replace maps while guest tests are running.

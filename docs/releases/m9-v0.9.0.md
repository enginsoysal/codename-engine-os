# Engine OS 0.9.0 — first VMware graphics delivery

**M9-GFX-VM-v1** prioritizes correct window movement and automatic supported VMware graphics/input setup. It adds bounded RAM composition, cached client movement, batched frame presentation, a separate cursor overlay, SVGA II presentation and VMware absolute-pointer input. Engine OS retains its own kernel and does not require VMware Tools. This is the first M9 slice; the broader hardware program remains in progress. Release qualification is recorded in the [exact-artifact acceptance report](../../evidence/M9/acceptance-results.json).

## Start here

Extract the entire ZIP, open **EngineOS.vmx**, start, select the disk row and follow Next. Review and install, then choose **Restart to Engine OS**. A new blank growable 20-GiB SATA disk is included. Keep Secure Boot off. The matching ISO may remain connected; no network or driver installer is needed. Use a fresh VM; cross-release app migration is unqualified.

On the installed desktop, navigate Home and Documents in Files, create a folder and drag Files by its title bar. Appearance controls style, accent and UI scaling. Scaling does not switch the physical firmware display mode. [Complete VMware guide](../handbook/install-m9.md), [graphics architecture](../architecture/graphics-m9.md), [remaining hardware stages](../milestones/m9.md).

## Verification scope

Owned VMware BIOS/UEFI fixtures perform real installation, retained-ISO restart, real folder creation, the original 7-Zip MSI lifecycle and two unforced disk-only boots with the same VM/NVRAM. Actual VMware pointer events drive repeated visible Files-window movement and confirm automatic video/pointer binding. QEMU native-framebuffer checks compare the moved window with an independent complete repaint at ordinary and actual 3840×2160 output. A separate 64-MiB BIOS journey exercises original Windows archive tasks.

Native movement checks require unchanged managed-page ownership, no idle repaint and both configured processors halted when idle. A separate over-cap 4096×2160 wizard boot verifies direct-framebuffer fallback when the optional buffer exceeds 32 MiB. This is wizard-only fallback evidence, not application qualification for that display profile. Host contiguous-allocation ownership/admission tests support these guest checks. Historical M4.5–M8 evidence and artifacts remain unchanged.

The optional retained framebuffer costs approximately 3 MiB at 1024×768, 3.9 MiB at 1280×800 and 31.6 MiB at 3840×2160. Admission preserves more than 24 MiB of free managed pages; other kernel, firmware, device and application memory is additional. Movement allocates no new screen/window backing buffers. Timing includes host test-observation overhead and must not be interpreted as monitor FPS or a guarantee for the owner's VM.

## Measured movement

On the same host, sequential QEMU TCG runs with two vCPUs, 128 MiB RAM, 1280x800 and 24 alternating moves measured median **682.8 ms (M8) -> 417.2 ms (M9)** and p95 **886.8 ms -> 541.4 ms**, approximately **39% lower** in each case. This includes QMP observation overhead; it is not VMware FPS. The real VMware test independently confirms correct visible movement and automatic binding. Its native 10-ms timer measured 71 ticks total across 24 moves in that run, with one 25-tick maximum; host remote-display capture adds substantial overhead. These are one-host observations, not a universal smoothness guarantee.

The actual 4K QEMU TCG test measured a median around **2.15 seconds** per observed move. It proves correct native 4K output and stable memory, **not real-time 4K performance**. Further acceleration and display work remain necessary.

## Limits

- CPU 2D composition and explicit compatible SVGA II presentation; no 3D, DirectX or universal GPU driver. Normal cached dragging uses RAM copies and one batched presentation.
- The firmware's physical display mode remains in use. Runtime display changes, SVGA3/MMIO and additional GPU families are future work. Stretching a low-resolution image in the VMware host can still blur it.
- Only supported VMware absolute-pointer semantics are added; wheel integration is separate. PS/2 and USB input remain available.
- The existing original 7-Zip 26.06 x64 console profile remains bounded. General MSI, Windows GUI, DOS and Windows 1–11 compatibility are not added by this release. [App guide](../handbook/windows-apps-m8.md).
- Physical machines, ARM/Raspberry Pi, factory Secure Boot and every VMware configuration are not qualified. A 48-MiB UEFI development attempt failed in firmware before Engine OS started; it establishes no OS minimum-memory support.
- Agent visual/scenario review is not a human usability study. Recognition alone does not qualify a device; the remaining M9 storage/network/audio/hotplug program is separate.

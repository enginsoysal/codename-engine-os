# Engine OS 0.8.0 — first original Windows MSI application

The **M8-MSI1-VM-v1** profile qualifies one original Windows console application: **7-Zip 26.06 x64**. Engine OS reads its original MSI inside the guest, installs its original payloads, executes the original `7z.exe` and `7z.dll`, creates/extracts a fresh sample ZIP, removes the product and installs it again. The matching [acceptance report](../../evidence/M8/acceptance-results.json) binds these claims to the exact files below. This is the first M8 delivery; the full DOS/Windows compatibility program remains in progress.

## Start here

Extract the entire ZIP, open **EngineOS.vmx**, start, select the disk row and follow Next. Review and install, then choose **Restart to Engine OS**. The included growable 20-GiB SATA disk is blank. Two CPUs, 128 MiB RAM and unsigned UEFI boot are configured; keep Secure Boot off. No network or host MSI execution is needed. Use a fresh VM; cross-release app migration is unqualified.

On the installed desktop choose **Start → Windows Apps → Install 7-Zip**, confirm, then **Open 7-Zip**. Use **Create test archive**, **Extract test archive** and **Remove app**. Your documents remain separate from product files. [Complete installation tutorial](../handbook/install-m8.md), [Windows app tutorial](../handbook/windows-apps-m8.md).

## What was verified

Guest installation and real executable/DLL execution are followed by independent inspection of all 106 original payload hashes and archived/extracted document bytes. Owned VMware BIOS and UEFI tests install, restart with the ISO retained, exercise the MSI lifecycle, then boot twice with the ISO disconnected and the same VM/NVRAM. QEMU covers actual native 3840×2160 output and a separate 64-MiB BIOS configuration. Cancellation, active memory pressure, memory-admission refusal, contained unsupported-operation failure and interrupted cleanup/recovery have separate reports. Host format and native-volume fault tests support those guest tasks; they do not substitute for them.

Resource measurements distinguish transient worker/writer pages from managed idle pages, static kernel/boot reservations and framebuffer memory. The Windows worker is created on demand and released after each task. Three warmed repeated original-executable runs must retain zero additional worker pages. Both configured guest processors halt when idle. UI progress refresh is capped at ten updates per second.

The captured resource workload measured **20,238,336 bytes** peak worker/writer pages during MSI installation and **5,443,584 bytes** for each warmed information run. No extra Windows worker pages remained after those runs. Managed idle pages measured 208,896 bytes; **this is not total OS RAM** and excludes static kernel/boot reservations and framebuffer memory. The acceptance report records the installed kernel's physical span separately. These measurements describe the named workload, not every archive input.

## Known limits

- Only the included, digest-pinned **7-Zip 26.06 x64 console profile** is accepted. This is a bounded MSI adapter, not a general Windows Installer service. The Windows 7-Zip file-manager GUI and Explorer extensions do not run.
- **Updating an existing ZIP is unsupported.** The example buttons always choose fresh numbered archives and extraction folders, preserving earlier results and avoiding that unsupported Windows codepath. Fresh create/extract, including repeated examples, is the qualified archive task; at most 100 numbered sample outputs are supported.
- Windows GUI, COM/services, guest drivers, DirectX, static TLS, Windows exception unwinding and multithreaded Windows applications are separate work. MS-DOS, Win16, Win32 and universal Windows 1–11 support are not delivered by this release.
- One Windows job/thread uses one assigned processor. Heap is bounded to 32 MiB, stack to 8 MiB and one random writer to 8 MiB; the managed worker page budget is 10,000 pages. These are caps, not idle consumption figures.
- Named x86-64 virtual profiles only. Physical hardware, ARM/Raspberry Pi, factory Secure Boot and arbitrary VMware storage devices are unqualified. There is one local account without authentication/native ACLs.
- Disk-full injection, arbitrary hostile PE/API fuzzing and modified-owned-file removal are not separately qualified. Native app capabilities retain their documented M7.4 limits. Agent visual/novice review is not a human usability study.

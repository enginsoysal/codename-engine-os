# M10 — hardware foundation and everyday desktop devices

Status: **in progress; no M10 release is qualified yet.** Owner-approved on
10 November 2026. This is the next hardware delivery, ahead of more Windows
application profiles. M9.2 remains the current tested download until M10 passes.

## Product goal

Install, connect supported devices and use them without finding a driver
installer or installing manufacturer control software. Engine OS supplies the
necessary original/adapted support and appropriately licensed firmware, loads
only needed runtime resources, and owns updates and recovery. Recognition is
not proof of usable functionality. Device support is qualified by exact
controller/protocol/function and complete user tasks, not just manufacturer.

The owner deferred the new product name. Keep Engine OS as the working name
and retain the existing working website and historical release identities.
Do not rename the repository, move domains or break old download links until
the owner chooses the replacement name containing Engine.

## This delivery: phases 1 and 2

Phase 1 introduces a bounded common hardware inventory and capability/status
contracts, automatic supported-device binding, visible Settings → Devices,
bounded buffers/deadlines, and useful failure/unsupported reporting. Existing
controller implementations remain the source of truth for actual capabilities.
Resource lifetime must handle disconnect and stale handles safely. No claim of
arbitrary driver plugins, comprehensive power management or universal recovery
is made from an inventory alone.

Phase 2 makes the everyday desktop usable on explicitly tested x86-64 virtual
profiles: ordinary/actual 4K presentation and readable scaling; working keyboard,
mouse and scroll; selected keyboard layouts; supported xHCI HID/hubs/reconnect;
writable USB storage with useful graphical file transfer and safe removal.
Existing IDE/SATA/SCSI/NVMe installation and independent startup must retain
regression proof on the new exact artifacts.

The first qualification is virtual, with VMware as the downloadable user
package and additional controlled QEMU USB/error cases. Physical devices are
separately qualified when tested. A virtual pass must never become an implicit
physical, ARM, vendor-GPU 3D or all-device compatibility claim.

## Required acceptance

1. New isolated M10 source/build IDs, ISO, VMware starter and hashes; preserve
   accepted M4.5–M9.2 binaries, tags and evidence.
2. Native Settings → Devices shows automatically discovered/bound devices,
   useful capabilities and explicit unavailable/limited states.
3. Real keyboard/mouse operation, scroll and implemented layout choices,
   including reconnect; ordinary tasks require no terminal.
4. Actual ordinary/4K framebuffer captures, measured desktop movement, correct
   repaint/scaling, bounded retained memory and halted idle processors.
5. Disposable USB media: connect, browse, copy a real file in both directions,
   flush, safe removal, reconnect and independent backing-byte verification.
6. USB disconnect/stale generation, read-only media, I/O errors, malformed
   metadata and quota/error recovery tests; no writes to unrelated disks.
7. New-artifact VMware BIOS/UEFI installation, persistence, retained-ISO restart
   and independent disk startup; existing original Windows app regression.
8. Current English architecture/handbook/status/release docs, GitHub publication
   and successful native website homepage/readback plus automatic article sync.

Host-only tests, an adapter name, a splash screen or a live-only desktop cannot
close these gates. Record failed/unqualified cases explicitly.

## Later hardware phases

3. Ethernet and Wi-Fi: actual address/DNS/TLS/download/reconnect tasks and a
   simple network picker; supported firmware delivered through the OS.
4. Audio: speakers/headphones/microphone, hotplug, device selection and bounded
   long playback, then HDMI/DisplayPort and Bluetooth audio profiles.
5. Vendor GPU families: qualified acceleration, memory management, graphics
   APIs/shaders, video, multiple displays and power/error handling.
6. Original Windows Steam client → install/login/download a selected original
   Windows game → GPU-accelerated play with sound/input → save/restart/resume.
   This also depends on the Windows API/DirectX compatibility program.
7. Laptops, docks, battery/sleep/resume, Bluetooth, controllers, cameras,
   printers/scanners/card readers and separately qualified ARM/Raspberry Pi.

Each phase gets its own exact tasks, device matrix, resource evidence and
release boundary. Anti-cheat/vendor service acceptance is not controlled solely
by the kernel. The target is broad integrated plug-and-play support, not a
promise that every existing/future device or game already works.

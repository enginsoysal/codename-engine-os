# M5.1 — guided setup and custom distributions

Scope: **M51-VM-v1**, extending the M5 native installation profile. Completion requires [exact acceptance](../../evidence/M5.1/acceptance-results.json), an actual custom-profile ISO and the public standard ISO tested in owned VMware guests. This is a keyboard-driven text interface, not the M6 desktop. An automated task route is not a human usability study.

## Concrete product requirements

1. A new user must reach Try, Install or Repair through displayed choices, without knowing terminal syntax, disk-sector tokens or what a placeholder means.
2. Disk selection must show real numbers/capacities, an explicit review before writing, a no-write back route and actionable errors. Raw details remain optional; the diagnostic terminal is reached deliberately and `menu` returns to setup.
3. A distribution author must build a differently branded, coloured, populated bootable/installable ISO through a validated profile. Unsupported features must be rejected, not silently treated as implemented.

The [product principles](../architecture/product-principles.md) apply to later milestones too. [Installation tutorial](../handbook/install-m51.md), [distribution tutorial](../handbook/distributions.md).

## Mechanisms and choices

The existing IRQ/HLT input loop feeds a bounded finite-state menu: welcome, file preview, disk selection, review, copying, completion, error, details, terminal and distribution information. Each page resets the existing small text buffer; there is no extra framebuffer allocation, browser, graphical toolkit or polling loop. A fixed 128-byte input buffer and static state retain the existing resource policy. Keyboard and serial input both use the same state transitions.

Installation/repair reuse the actual M5 preflight and write path, including target identity/capacity/snapshot binding, blank-target refusal, intent/completion records, flushes and byte readback. The menu generates the internal confirmation rather than asking a novice to type sectors. Back invalidates the plan. Progress is bounded to percentage milestones; 100% occurs only after the completion write/readback/flush succeeds. Errors never pretend that an incomplete install is usable.

Try mode provides real create/read/list operations on a sample note. It clearly distinguishes temporary live changes from installed persistence. Advanced storage commands remain available; they are not the normal install interface. Successful completion explains exactly how to power off VMware, disconnect live media and start the installed disk. Automatic host-VM control, media ejection and automatic reboot are not implemented.

## Distribution profile version 1

`distros/engineos.json` is the standard profile; `distros/forge.json` is a working alternative. `python tools/build/m51.py --profile distros/forge.json` validates and builds an independent ISO/USB image and manifest under `dist/profiles/forge/`. Profiles select an ASCII name/version/welcome message, an RGB accent and data packages/files. Selected inputs and contents are hashed into the build identity, compiled into branding and placed into the native live and installed filesystem. `/System/Distro/profile.json` records the exact recipe and input/file digests.

Data packages are real selected files, not a general application/package manager. The native console/recovery/storage implementation remains mandatory. Desktop/compositor choices, arbitrary executable packages, repositories, dependency resolution, runtime theme editing, Windows apps and binary plugin ABIs are future work. The MIT kernel source can independently be forked/modified; no profile claims unsupported capabilities.

Validation rejects unknown fields/hooks/packages, escaping host sources, invalid/reserved target roots, duplicate targets/packages, invalid colours and oversized files before compilation/media authoring. Inputs stay under `distros/`; additional data targets stay under `/Users/test/Documents/` or `/Data/Packages/`. At most eight packages and 32 files are admitted, each at most 48 KiB. The small ASCII renderer limits branding strings; full internationalization/accessibility requires later UI work. Profiles cannot remove disk review, recovery guards or explicit confirmation.

## Qualification and unchanged limits

Task-driven tests use only displayed numeric choices for Try, install, cancel, persistent note and boot repair. Real write EIO exercises the readable error/details route. A distinct Forge build proves colour/branding, selected package content and detached installed boot. Profile negative tests reject unsafe/unsupported recipes. Native overlay quota/reclamation, CPU halt observations, BIOS/UEFI ISO/USB and owned VMware EFI/BIOS with a new **20-GiB SATA disk** provide runtime evidence.

The M5 storage/trust boundary remains: SATA/AHCI 512-byte install targets, 64-MiB ESP, 16-MiB native ext2 data, 48-KiB files, remaining capacity unallocated, 512-KiB live modified-page budget, unsigned media and same-build boot repair. Physical hardware, general upgrades/rollback, crash atomicity, desktop/network and Windows 95–11 execution remain unqualified or unimplemented. Earlier M5/M4.5 releases and frozen evidence remain unchanged.

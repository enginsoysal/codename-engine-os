# M4.5 physical qualification procedure

Status: not executed. No physical test machine or disposable physical disk has been designated. VM reports cannot fill this acceptance record. The development computer is not an implicit test target.

## Profile required before execution

Record the designated computer, CPU/ISA, installed RAM, firmware revision, available UEFI/BIOS modes, Secure Boot state, storage controller/protocol, logical sector size, USB controller/topology and display mode. Record the exact release, build ID and downloaded media hashes. Identify a separate disposable removable boot medium and, if storage tests are wanted, an explicitly overwritable test disk by physical label and capacity. Existing disks are discovery/read-only targets unless separately designated.

Start with the normal unsigned preview and Secure Boot disabled only on the designated test machine. Preserve its original firmware settings and recovery instructions. Do not infer that every firmware offers legacy BIOS or custom key enrollment. Owner-key tests require the separate machine-specific policy below. The existing enrollment helper is deliberately VM-only and must not be used on physical firmware.

## Execution and evidence

1. Verify the release hashes before writing a boot medium. Select only the designated removable target with a trusted imaging tool; record its identity and the tool result. ISO optical boot and raw USB-image boot are separate cases. There is no Engine OS installer yet.
2. Boot UEFI without Secure Boot, and legacy BIOS only where actually supported. Capture the native build ID, loader/kernel entry, console and any rejection diagnostics. A firmware menu alone is not a passing boot.
3. Run `help`, `info`, `hardware` and `disks`. Preserve the output. Check controller binding and initialization status against the recorded hardware. Unrecognized hardware is a failing or unsupported profile, never successful discovery by inference.
4. Read known FAT32/ext2 fixture files from a designated test disk, including known file bytes and sector geometry. Compare before/after backing hashes with an independent trusted system. Ordinary disks must remain unchanged. Do not invoke development-volume write tests against a user's disk.
5. Test direct keyboard/mouse input, a designated USB hub and BOT/UAS storage where available. Exercise repeated idle disconnect/reconnect, stale disk references, healthy replacement and measured page counts. Unplug-during-DMA and power interruption need their own explicitly disposable fixture; a normal reconnect does not qualify them.
6. Capture retained and peak managed-page counts, boot reservations, framebuffer size, CPU count and actual idle behavior. Managed pages are not total machine RAM. VM emulator CPU samples cannot stand in for physical CPU/power measurement. Compare repeated reconnect cycles for retained growth.
7. Record pass/fail/unsupported for each case, logs/screenshots, exact reproduction and known limitations. A failing machine keeps that profile open. Re-run affected cases after fixes with the new build identity.

## Owner Secure Boot qualification

Before any physical key change, the owner must designate the machine, export/preserve its existing PK/KEK/db/dbx policy, establish firmware recovery, and select protected production signing identities and custody. Document the machine's actual enrollment/recovery interface and explicitly approve that concrete policy. Factory trust needs a separately accepted OEM/Microsoft signing route; self-signing does not provide it.

The physical matrix must prove valid signed boot, unsigned/modified-loader rejection, changed kernel/init rejection, an authorized payload update with the same enrolled signing policy, rejected foreign identity, and the chosen rotation/revocation/recovery procedure. Disposable VM keys do not become production credentials. No private key, firmware-variable export or enrollment medium belongs in a public release.

## Completion rule

Publish a sanitized report per designated profile with build/media hashes and actual results. Keep the full milestone open until the agreed physical/trust acceptance has evidence. A finite tested matrix establishes those profiles; it cannot establish operation on every existing or future device. Windows 95–11 application compatibility remains a separate unimplemented compatibility roadmap.

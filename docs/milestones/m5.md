# M5 — native live installation and recovery

M5 implements installation, not a demonstration installer screen. The current acceptance profile is **M5-VM-v1**, extending the established x86-64 VM scope. Final completion requires the [acceptance report](../../evidence/M5/acceptance-results.json), exact artifact hashes and all runtime gates. [User installation tutorial](../handbook/install.md), [recovery](../handbook/recovery.md), [commands](../handbook/m5-console.md).

## Delivered mechanisms

- BIOS/UEFI optical and USB live media, using the original loader/kernel and existing native drivers. No Linux, Windows or FreeBSD kernel is included.
- A volatile native filesystem backed by immutable sparse template pages and a maximum of 128 modified four-KiB pages. Ordinary live file commands never silently mount an installed disk writable.
- SATA/AHCI, 512-byte-sector installation on a blank disk between 256 MiB and the version-1 upper bound of 2 TiB minus one sector. The capacity limit is an implementation bound, not proof of every capacity/controller. Other discovered transports remain inspectable, not install targets.
- An explicit target/change plan followed by an exact disk-number/capacity confirmation. Cancel, missing plan, bad confirmation, nonblank boot metadata, undersized and unsupported targets cause no installer writes. Revalidate the descriptor and sector-zero snapshot immediately before starting.
- GPT primary/backup tables, original BIOS boot area, a 64-MiB FAT32 ESP with `EFI/BOOT/BOOTX64.EFI`, and a separately formatted 16-MiB native ext2 partition. Other capacity stays unallocated. This is not secure erasure, a partition editor or a dual-boot installer.
- Independent installed boot with installation media absent and fresh firmware variables. The installed and live kernels share source/build identity, but differ in bundled installer payload: the installed kernel omits it.
- Persistent native file operations through an explicitly selected, validated installed volume. More than one eligible SATA target is refused for automatic persistent mount: the old boot header does not carry firmware boot-disk identity, so guessing would risk selecting a different disk. GPT copies and native ext2 metadata are checked before writable mount.
- An intent/completion record, byte-for-byte copy readback, flushes, and same-build boot repair from live media. Repair preserves the complete native data partition once initialized. An interrupted initial installation can initialize that partition only when the durable intent says it has never been initialized.

## How and why

The live kernel carries an original sparse installation bundle: zero pages use a four-byte record, other pages carry four KiB. This keeps firmware/optical access out of the running kernel and requires no ATAPI write support, host installer or large decompression workspace. The original two-MiB BIOS kernel bound remains enforced. Bounds/order/CRC are validated before writes; CRC detects accidental corruption, not malicious authorship. Release SHA256 identifies the distributed image; public media are unsigned.

The bounded M4 ext2 implementation is reused for a real writable native volume. This avoids claiming new filesystem integrity features while adding installability. The 16-MiB volume, 512 inodes and 48-KiB maximum file size are deliberately visible limits. Large storage, application packages, richer metadata and journaling require later filesystem work. The trusted diagnostic console does not implement multi-user filesystem ACLs.

Boot code is outside the writable native volume. `/System/Versions/<build-id>/version.txt` and `/System/Current/version.txt` record the selected release in that namespace; these are metadata directories, not a general executable mount manager or protected symbolic link. Live edits are never copied into the installed image.

## Version-1 activation/recovery format

All integers are little-endian; logical sectors are 512 bytes. GPT occupies sectors 0–33 and the last 33 sectors. Sector 40 is the durable installation intent; sector 41 is the verified-complete record. Each record is 512 bytes:

| Offset | Field |
|---|---|
| 0 | Eight-byte `ENGM5V1` plus NUL magic |
| 8 / 12 | Format version 1 / state: 1 pending, 2 complete |
| 16 | Target sector count, uint64 |
| 24 | Exact source build ID, 32 ASCII bytes |
| 56 | Per-install disk GUID, 16 bytes; not a cryptographic identity |
| 72 | Generation, uint64; initial generation 1 |
| 80 / 84 | Sparse boot payload CRC32 / data-initialized flag |
| 88 / 96 | Native data first sector / sector count, uint64 |
| 104 / 136 | Active / previous build IDs, 32 bytes each |
| 508 | CRC32 of bytes 0–507 |

BIOS stage 2 begins at LBA 64; raw installed kernel at LBA 128. The ESP starts at LBA 8192; data at LBA 139264 for 32768 sectors. A completed first installation has active=current, previous=zero. Version-1 repair restores that same build; it never activates an unknown version. This defines the activation/rollback wire fields without claiming a working arbitrary upgrade/downgrade engine. Cross-version staging, automatic rollback and atomic activation remain future work.

The completion record is invalidated before copy. A body-copy failure leaves a pending installation; success is reported only after final completion write/readback/flush. If that final I/O fails, the durable completion outcome can be unknown: no success is reported, and live recovery is required. Boot metadata and files are not one atomic transaction: arbitrary power cuts can leave an unbootable disk. The live ISO is the recovery entry point. Boot repair does not repair dirty/corrupt ext2 data; preserve an offline image and use the separate conservative filesystem recovery procedure.

## Acceptance boundaries

Required: actual ISO/USB live boots; BIOS/UEFI installation and media-detached boot; persistent file across two boots; plan/cancel/refusal hashes; real copy EIO followed by successful resume; same-build repair with an unchanged whole-data-partition hash; native overlay quota/reclamation; halted CPUs and separate image/managed-memory accounting; the exact public ISO tested in owned VMware guests; English tutorial/commands/downloads and current GitHub publication.

No physical hardware, factory Secure Boot, arbitrary storage controllers/capacities, dual boot, general partition management, filesystem power-loss atomicity, desktop/network, ARM or Windows binary compatibility is implied. Windows 95–11 remains the existing version/architecture/task-qualified requirement for later milestones.

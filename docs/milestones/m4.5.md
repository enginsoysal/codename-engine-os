# M4.5 — broader boot and hardware qualification

**In progress. Not complete.** This milestone closes the gap between M4's bounded development profile and general boot/storage discovery before the M5 installer. Historical M0–M4 completion labels refer only to their published test scopes; they do not establish universal device support.

## Agreed acceptance work

| Track | Required result | Initial state |
|---|---|---|
| UEFI ISO/USB | x86-64 own-kernel boot on a broader named firmware/media matrix | Existing narrow QEMU/VMware evidence only |
| Secure Boot disabled/enabled | Signed loader, verified loaded code, key/trust policy and explicit enrollment instructions; negative tamper tests | Not implemented |
| Legacy BIOS | Separate x86 boot path reaching the original kernel, not a UEFI compatibility claim | Not implemented |
| General disk discovery | Actual capacity and logical sector size, ordinary unmarked disks, multiple devices; explicit empty/unsupported/error states | M4 accepts only a marked writable 16 MiB profile |
| Storage protocols | Broader AHCI, NVMe, USB mass storage and named virtual storage controllers with transfer evidence | AHCI development profile only |
| Partition discovery | Bounded GPT/MBR validation, CRC/range/overlap checks and explicit damaged/empty/unknown results | Not implemented |
| Filesystems | Extended ext2 profile, FAT32 reading, explicit NTFS/exFAT recognition/support boundaries | Restricted ext2 only |
| Hardware inventory | Devices, driver binding/capability and initialization failures; no silent success based on class alone | No general inventory |
| Input/display | Broader PS/2/USB, connect/disconnect scenarios and framebuffer resolutions on named profiles | Boot-attached QEMU HID only |
| Failure handling | Missing devices, invalid firmware/metadata, I/O faults and timeouts | Narrow M4 paths only |
| Efficiency and practical matrix | Actual QEMU, VMware and explicitly designated physical-machine results; CPU/RAM/idle accounting | No physical machine designated |
| Publication | English architecture/usage/status/evidence and verified GitHub artifacts | Required after each coherent increment |

Secure Boot with owner-enrolled keys is distinct from booting on factory trust stores without key changes. Our own signature does not create firmware trust. ARM64/other ISAs remain separate ports; this milestone is x86-64. A virtual-device result is never substituted for a physical-machine result.

Ordinary-disk inventory and reads must not depend on an Engine OS marker or fixed capacity. Detection is separate from supported data transfer and from a mountable filesystem. Unknown/corrupt media must remain inspectable with a clear status. Write authorization remains explicit: detecting a disk never authorizes formatting it. Existing marked development volumes can retain their tested write path while arbitrary media remain read-only. Partitioning, formatting, target selection, installation and independently booting an installed system remain M5.

Each row stays open until its code and named runtime tests exist. Physical tests require an explicitly designated disposable test machine/device; neither the development host disk nor a user's existing VM disk is an implicit target. Missing external qualification remains visible rather than being waived to declare completion.

## Current increment

The [first storage/trust increment](m4.5-storage.md) implements ordinary AHCI and original NVMe reads, GPT/MBR validation, FAT32 reading and owner-key Secure Boot test infrastructure. See [runtime evidence](../../evidence/M4.5/README.md). This does not close BIOS, USB/virtio storage, wider filesystem/input profiles or physical/factory-trust qualification. The published M4 release and default launcher remain separate historical/current stable paths.

# M4.5 original BIOS and dual-firmware media

M4.5 remains in progress. This document describes the x86-64 boot increment, not an installer or universal firmware qualification.

## Layout and handoff

`boot/bios/` contains the original real-mode MBR, second stage and freestanding 32-bit preparation code. `tools/build/bios.py` uses the pinned LLVM tools to produce them. No GRUB, FreeBSD or Linux boot code is embedded. The existing original UEFI loader remains the other entry point. Both paths load the exact same kernel and versioned 160-byte boot contract.

The hybrid ISO has separate BIOS and EFI El Torito entries. Its BIOS first stage loads a bounded 32-KiB second stage using BIOS EDD reads with 2048-byte medium sectors. The GPT USB image retains the protective MBR and GPT; its ESP begins at 4 MiB and a separate BIOS Boot partition contains the second stage and flattened kernel. Its EDD path requires 512-byte medium sectors. Actual reported sector size is checked before loading. Unsupported EDD/geometry is rejected rather than interpreted with wrong offsets. This is boot-media layout, not a general disk formatter or installed-system layout.

The BIOS second stage enables A20, obtains a bounded E820 memory map, checks available memory covering the kernel destination before copying, and reads the flattened kernel in 32-KiB chunks. It validates the raw kernel CRC, normalizes nonoverlapping E820 regions into the shared memory-descriptor format and reserves its own structures, stacks, page tables, AP trampoline and kernel. CRC detects accidental corruption; it supplies no Secure Boot authenticity. Original temporary page tables cover the kernel's initial 4-GiB supervisor window. CPUID long-mode/NX checks precede the 64-bit transition.

A checksummed ACPI RSDP is found in the BIOS-defined ranges. VBE supplies a supported 32-bit RGB/BGR framebuffer; unavailable graphics leave serial diagnostics. Tests select 640x480, 800x600 and 1024x768 BIOS modes as well as the UEFI profile. The 64-bit entry uses the same code/data selectors expected by the kernel exception-return path. The common handoff avoids a second kernel architecture while keeping firmware-specific discovery outside the kernel. The BIOS path does not call UEFI services and is not called Secure Boot.

## Memory choice

The M45 UEFI loader frees the temporary ELF input allocation after copying and validating its loadable segments, before ExitBootServices. It removes only that exact reservation; kernel, init and remaining handoff resources stay reserved. This avoids retaining both the ELF file and its loaded image. BIOS loads the bounded flattened image directly into its reserved kernel destination. Tests separately record boot reservations and managed retained/peak pages at the pre-USB storage checkpoint; these figures exclude firmware-owned memory, the framebuffer, emulator overhead and later USB allocations. Configured VM RAM is not kernel consumption. In the current two-CPU QEMU ISO profile, the UEFI input-buffer release reduces boot reservations to 480 KiB; BIOS reserves 520 KiB. At that checkpoint both retain 108 KiB of managed pages with a 456-KiB workload peak. Exact build-specific values remain in the reports.

## Verification and boundaries

Run `python tests/m45/boot_matrix.py` and `python tests/m45/bios_negative.py` after `python tools/build/m45.py`. The matrix starts the same ISO/USB images through pinned OVMF and SeaBIOS, requires native runtime completion and inspects actual HLT state on all CPUs. Separate negative cases exercise damaged raw kernel CRC, damaged handoff CRC, unavailable destination memory and medium-sector mismatch. Serial-only fallback is also exercised. Reports and actual screenshots are under [boot evidence](../../evidence/M4.5/boot/results.json).

This establishes named QEMU firmware profiles only. The separate VMware Workstation 26.0.1 build 25688693 matrix boots this same ISO through EFI/BIOS with SATA and IDE, plus EFI/NVMe, at two CPUs/128 MiB. It requires native completion and a verified ordinary first-sector read; it is not a VMware USB/input or full storage error/queue qualification. Existing VM inventory and ordinary backing-file hashes remain unchanged. Physical firmware, factory-trusted Secure Boot and arbitrary removable media remain separately qualified work. Normal development ISO/USB images are unsigned; owner-key Secure Boot tests use separate signed media and disposable VM policy. There is no installer, disk selection or installed-system boot in this increment.

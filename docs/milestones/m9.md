# M9 — automatic hardware, starting with responsive VM graphics

Status: **first graphics delivery qualified within M9-GFX-VM-v1; broader M9 hardware program remains in progress.** The owner moved this ahead of further Windows application work on 9 November 2026 after reporting unattractive, stuttering folder-window movement in VMware. [Twelve-gate acceptance](../../evidence/M9/acceptance-results.json), [release/downloads](../releases/m9-v0.9.0.md), [installation guide](../handbook/install-m9.md).

## First delivery: M9-GFX-VM-v1

The immediate target is visible, responsive native desktop movement on named virtual profiles, with no manual guest driver installation. Diagnose rendering and input before attributing every delay to the GPU. Recognition, driver binding and useful device operation are separate results.

- Compose antialiased text/surfaces in one optional bounded RAM framebuffer, avoiding repeated video-memory reads. Retain a direct-framebuffer fallback when the buffer cannot be admitted. Count the buffer as retained managed memory; it is not free video RAM.
- Reuse unchanged front-window interior pixels during movement. Redraw exposed regions, rounded borders and shadows correctly. Resize, changed content and unsuitable scaling must fall back to exact composition.
- Keep the cursor as a separate visible overlay. It must not be copied into a moved window or force an unrelated large repaint.
- Automatically select the compatible VMware SVGA II 2D presentation protocol. Validate the firmware framebuffer, FIFO ranges and supported operations, use bounded waits and retain a fallback. This is not a 3D/DirectX driver.
- Automatically enable the supported VMware absolute-pointer interface, retaining PS/2 and USB paths. Pointer coordinates, display scaling and button transitions must agree.
- Verify installation and installed restart, real folder navigation, movement correctness, resource/idle behavior and original M8 app tasks on the new artifacts.

Release requires measured native motion and real VMware guest input, real ordinary/4K framebuffer evidence, source/artifact identity, honest limitations, current English guides and a tested ISO/VMware package. A driver label or screenshot alone is insufficient. The exact original owner VM and every physical device are not implicitly qualified.

## Remaining hardware program

1. Unified bus/device inventory with useful active/limited/unsupported states.
2. Automatic capability-based binding, dependencies and on-demand lifetime.
3. Broader storage, input, wired networking and audio, each through useful tasks.
4. Safe hotplug, reconnect, resource reclamation and fault recovery.
5. Additional virtual/physical GPU families, acceleration and display changes.
6. Separately qualified Wi-Fi, Bluetooth, cameras and other device classes.

These remain independent follow-ups. Standards permit shared class drivers; a device class name alone does not describe a vendor-specific programming interface. Engine OS should provide the supported drivers automatically rather than making users find installers.

## How and why

The earlier CPU compositor blends directly in scanout memory and repaints large unions of old/new bounds. It can therefore perform expensive video reads and repeat font raster work on every movement. A RAM composition buffer plus cached interior movement addresses that path without requiring a complete 3D stack. One screen buffer is simpler and smaller than full per-window backing surfaces; admission reserves memory for useful application work. The framebuffer consumes approximately 31.6 MiB at packed 3840×2160, and approximately 3 MiB at 1024×768. Idle must still halt; no continuous animation or device polling is added.

Public protocol references: [VMware SVGA device interface maintained in Linux](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/vmwgfx/device_include/svga_reg.h), [VMware pointer protocol implementation maintained in Linux](https://github.com/torvalds/linux/blob/master/drivers/input/mouse/vmmouse.c). Engine OS's new implementations are original code; upstream driver source is not imported.

## Qualified measurements

Actual ordinary/3840x2160 moved frames match independent full repaints. Native dragging retains no additional managed pages and idle stops repainting with both processors halted. Real VMware loopback pointer events move the visible window while SVGA II and absolute-pointer binding are active. The paired QEMU TCG ordinary-resolution observation reduced median event-to-composition time by about 39%; this is one host observation, not monitor FPS or a universal smoothness guarantee. The 4K TCG run verifies correctness, not real-time performance. Historical M4.5-M8 proofs and binaries remain unchanged.

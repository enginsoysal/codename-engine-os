# M4.5 owner signing, update and trust boundary

Normal public preview ISO/USB images are unsigned and require Secure Boot disabled. Owner-signed UEFI media are built separately under ignored output. Neither a self-signature nor the VM tests establishes OEM/Microsoft factory trust.

## Persistent signing identity

After `python tools/build/m45.py`, the signing builder can reuse an owner-provided PFX and an independently approved SHA-256 certificate pin:

```powershell
python tools/build/secure.py --owner-pfx "<protected-owner.pfx>" --owner-sha256 "<64 lowercase hex characters>" --work-name owner-release
```

The command prompts for the PFX password. Noninteractive callers can supply `ENGINE_OS_PFX_PASSWORD`; the builder removes that value from its own environment before starting child tools. Passwords are never passed in command-line arguments or provenance. It validates the certificate pin, matching RSA private/public key, minimum 2048-bit RSA size, validity period and code-signing usage. It also requires current source/kernel hashes and the exact native init contract to match the build. A missing/wrong owner identity fails; it is never silently replaced by a new identity.

`tools/build/owner.py` keeps the host certificate store unchanged. The pinned SignTool adapter uses an owner-only NTFS temporary directory and a one-use plaintext PFX, removed on success and failure. The signing computer must be trusted: deletion is not a secure-erasure guarantee and the key is present in process memory. This is a local PFX adapter, not an HSM or remote signing service. Production private-key custody and protected/offline signing remain the owner's operational policy.

The selected owner media are in `build/m45/owner-release/signed-media/`. A signed loader pins the exact external kernel and init SHA-256 values. A payload update requires rebuilding and signing that loader with the same approved identity. Keep the public certificate pin/provenance with the release review. Never publish PFX files, private headers, enrollment helpers, test-negative media or firmware-variable stores. Normal automated GitHub preview publication selects only the unsigned `dist/` assets.

Without owner arguments, `secure.py` deliberately creates a new disposable VM test owner. That default is not a production identity generator. Its TCG-only enrollment helper refuses physical execution and nonempty existing PK/KEK/db policy. It must never be used to enroll a physical computer.

## Runtime qualification

`python tests/m45/secure_boot.py` contains 23 checks using pinned QEMU/OVMF and disposable private firmware-variable copies. It checks valid owner boot, unsigned/modified loader rejection, changed kernel/init rejection, existing-policy refusal and verification even with Secure Boot disabled. It then exercises an encrypted persistent identity, wrong pin/password refusal, temporary-private-file cleanup on signing failure, and a changed authenticated init payload under the original enrolled policy. An old signed loader must reject that changed payload until its signed digest is regenerated.

The firmware-policy tests use original TCG-only code in `tests/m45/firmware/policy.c`. A KEK-authorized authenticated db replacement installs a new image signer; exact db bytes are read back while PK and KEK remain unchanged. The new signer boots, the retired image signer is denied, a trusted image signer cannot exercise KEK authority, and foreign/replayed db updates are refused. An explicit original VM policy snapshot restores the original signed boot. That snapshot test is not a physical firmware recovery procedure. The fixture initially shares one authority identity for PK/KEK; after db rotation the image and authority roles are distinct. Production key hierarchy/custody is not inferred from the fixture.

[Current runtime results](../../evidence/M4.5/secure-boot-results.json) include build identity, public certificate/payload hashes and test-source provenance. Authentication is not version rollback protection; installed update activation and version rollback policy remain M5. The interface reference is [UEFI 2.11 Secure Boot and Driver Signing](https://uefi.org/specs/UEFI/2.11/32_Secure_Boot_and_Driver_Signing.html), including authenticated db updates and authority roles. Only the named VM behavior is qualified here.

## External acceptance still required

A real owner must designate a test machine, preserve its existing trust databases, select the production PK/KEK/image-signing hierarchy and custody, and establish its exact enrollment/recovery procedure. Physical tests must verify those choices on that firmware; the VM helper deliberately cannot perform physical enrollment. No host disk, host firmware, global certificate store or existing VM is an implicit test target.

Factory trust without owner enrollment needs a signing route accepted by the intended OEM/Microsoft database. No accepted signature, service identity or authorization has been supplied. Physical boot/storage/input results and physical owner-key enrollment/rotation/recovery therefore remain open. A local self-signature cannot close these requirements. Full M4.5 remains in progress.

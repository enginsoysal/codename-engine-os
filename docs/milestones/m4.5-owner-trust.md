# M4.5 owner trust policy and qualification boundary

The implemented Secure Boot route is an owner-enrolled disposable VM test. It does not enroll a production computer or obtain Microsoft/OEM factory trust. Normal preview ISO/USB images remain unsigned and require Secure Boot disabled.

## Reproduce the implemented enrollment route

After `python tools/build/m45.py`, run `python tests/m45/secure_boot.py`. The script verifies pinned firmware/signing tools, creates an ephemeral test certificate and private PFX under ignored `build/m45/secure`, signs a digest-pinned EFI loader, creates enrollment media and launches only owned TCG VMs. It starts from fresh disposable firmware variables, requires empty SetupMode PK/KEK/db, enrolls db then KEK then an authenticated PK update, and checks actual SecureBoot=1/SetupMode=0 on the subsequent signed boot. Existing platform policy is a tested refusal case. It never imports a key into the host certificate store or host firmware.

The signed loader contains SHA-256 digests of the exact external kernel and init image. Every payload change requires regenerating those digests, rebuilding and signing the loader. Tests verify unsigned/modified loader rejection by firmware and modified kernel/init rejection by the verified loader. A payload CRC does not replace this authentication chain. Each run rotates its disposable test owner: this is reproducible qualification infrastructure, not a persistent production update identity.

## Production decisions still required

A real owner must designate a test machine and its firmware recovery/enrollment procedure. Existing trust databases must be inventoried and preserved before any approved changes; the current TCG-only helper deliberately cannot perform that work on a physical computer. Firmware-specific instructions must be verified on that exact machine rather than guessed. Production PK, KEK and image-signing identities, protected/offline private-key custody, expiration/rotation, revocation and rollback/recovery requirements remain separate owner policy decisions. The VM test reuses one disposable identity for convenience and is not the production key hierarchy.

A production build must preserve the approved signing identity across updates, authenticate every loaded executable payload and verify the signed media against the intended enrolled policy. The current tests do not qualify key rotation, revocation or rollback on physical firmware. M5 update activation/recovery is separate from M4.5 boot authentication. Private signing keys, PFX files, enrollment helpers/media and existing firmware variable stores are never release assets.

Factory trust without owner enrollment requires a signing/trust route accepted by the intended OEM/Microsoft firmware database. No such signature, service identity or authorization has been supplied; a self-signature cannot substitute for it. Factory-trusted boot and physical enrollment therefore remain explicitly open, preventing full M4.5 completion. No development-host reboot, disk or firmware change is an implicit test action.

# M2 — protected native processes and efficient resource use

M2 builds on the own UEFI kernel. It executes real CPL3 native programs in separate address spaces, isolates failures, mediates object rights and publishes a new normal-mode ISO. This is still a development kernel, not a Windows-compatible desktop or installer. [Status](../roadmap/status.md), [evidence](../../evidence/M2/README.md).

## What you see

After boot, a finite self-verification workload runs automatically. The screen reports `M2 KERNEL ONLINE`, `USERMODE ISOLATION: PASS`, private-memory/shared-IPC checks, contained user faults, process starts and managed-memory peak/retained KiB. The final kernel idle state uses HLT; the screen remains visible. There is no shell, keyboard handling or installation menu yet.

[Download M2 prerelease](https://github.com/enginsoysal/codename-engine-os/releases/tag/m2-v0.2.0). Validate the image against `M2-SHA256SUMS.txt`.

## VMware test

1. Power the VM fully off and select the new `EngineOS-M2.iso` as its CD/DVD image; connect it at power on.
2. Use a 64-bit UEFI configuration, Secure Boot disabled. The user's earlier FreeBSD 15 64-bit profile booted M1; that guest label does not supply a FreeBSD kernel.
3. Start with one vCPU and 128 MiB RAM. A 64 MiB case passes on QEMU; VMware firmware can have different requirements, so increase guest RAM if its firmware requires it.
4. Boot the EFI optical drive and wait for the M2 result screen. Close/power off the VM to stop.

M2 is automatically qualified in QEMU, not claimed fully VMware-qualified before the user's test. If it fails, capture the screen and ideally a serial-port log. No real host disk is required or exposed. This ISO cannot install to a virtual disk yet; M5 supplies that workflow.

## Build/run and files

```powershell
python tools/build/m2.py
python tools/vm/run.py
python tools/vm/run.py --ram 64
python tools/vm/run.py --usb
python tools/vm/run.py --debug
python tests/m2/verify.py
```

The launcher defaults to M2, one vCPU and 128 MiB; `--milestone M1` selects the historical path. Debug pauses at start with loopback GDB on port 1234. [Tool setup](../../tools/README.md).

Generated `dist/` files: `EngineOS-M2.iso`, `EngineOS-M2-usb.img`, kernel ELF/map, native user ELF, `m2-build-manifest.json` and `M2-SHA256SUMS.txt`. Firmware/QEMU and proprietary applications are not bundled. Artifacts are ignored by source Git and uploaded to the release separately, with remote SHA-256 verification.

## Mechanisms, how and why

| Mechanism | Implementation and rationale | Explicit boundary |
|---|---|---|
| Physical pages | Two 32 KiB bitmaps, zero-on-allocation and checked release, conventional RAM below 1 GiB | No early firmware/loader reclaim or general pressure policy |
| Kernel map | RX text, RO/NX constants, RW/NX data, missing null page, guarded 16 KiB entry stack, CR0.WP/EFER.NXE | Low identity development layout, not a final higher-half/SMP design |
| User isolation | Private CR3/page tables/data/stack and absent stack guards | One context per process, no threads/TLS/preemption |
| Shared code | One immutable copy of native code/constants mapped into each process | Only the embedded fixed native ELF profile is accepted |
| User entry | TSS privilege stack, DPL3 gate, saved context, checked IRETQ | Native64 only; temporary `int 0x80` ABI transport |
| Syscalls | Status in RAX; checked output buffers; overflow/permissions/page-by-page copies | No Windows calls, filesystem or arbitrary executable loading |
| Handles | Slot/generation, type and read/write/transfer rights; reduced-right duplicates/transfers | No identities/ACLs or guest handle ABI yet |
| IPC | Four 32-byte messages per mailbox, explicit shared memory/maps | Nonblocking empty/full status, not scheduler-backed waits |
| Cleanup | Drop handles/mapping references, switch out before freeing tables, zero reused pages | Boot reservations and common kernel pages stay retained |
| CPU policy | One active CPU; finite cooperative probes; HLT after completion | A non-yielding arbitrary app can starve peers until M3 preemption |

Native user mappings start at 4 GiB, above the retained low-4-GiB supervisor identity window. The guarded kernel entry stack uses an upper-half mapping shared by every address space, and execution moves to it before the first CR3 process switch. This avoids collisions with firmware/boot stacks in larger VMs. Future 32-bit guest profiles still need a suitable separate layout; reserved IDs are not working PE32 support. Unconfigured SYSCALL is disabled and legacy SYSENTER has no valid selector, so neither bypasses the implemented native gateway.

The shared kernel-entry stack is safe only within this non-reentrant, single-active-CPU model. Future preemptible/SMP entry requires per-CPU/thread handling. Native profile IDs are trusted loader state; reserved Win16/Windows x86/x64/Linux/Darwin IDs do not imply implemented decoders.

## Actual workload and acceptance

Thirteen initial processes share native code and have private data/stack pages at the same virtual addresses. Producer/consumer exchange a message and a reduced-right shared-memory handle. The receiver reads after closing its handle (mapping keeps the reference), then attempts a forbidden write. Other roles attack kernel text, executable stack, stack guard, user text, I/O privileges, CLI, disabled SYSCALL/SYSENTER entry and an invalid noncanonical return stack. These ten hostile cases are contained. A producer and survivor continue; 32 additional fresh survivor processes exercise page reuse.

Expected totals: 45 starts, 35 clean exits, ten contained failures, no test assertions and balanced object/page accounting. Separate operations check handle generation staleness, rights escalation/type errors, all 16 handle slots/full quota, 128 repeated object cycles, four-entry IPC saturation, unknown syscalls, kernel/overflow/cross-guard/read-only output pointers and private sentinel state. This is deterministic native verification, not a claim to support hostile arbitrary applications or every race.

## RAM and CPU accounting

- `peak_owned_bytes`: peak pages allocated by the M2 allocator, including process page tables/data/stacks/shared pages and common kernel mapping pages.
- `retained_owned_bytes`: managed pages left after every test process/object is cleaned up; currently the common kernel mapping/entry-stack baseline.
- `boot_reserved_bytes`: separately retained loader, staged ELF, kernel image/static metadata, initmanifest, boot stack/map/tables. Never hide this behind a small managed-page number.
- Neither category includes all firmware/device/framebuffer reservations or host-QEMU memory. Configured guest RAM is not the kernel footprint.

Current qualification targets: managed peak ≤512 KiB, retained managed ≤64 KiB, boot reservations ≤1 MiB and managed peak+boot ≤2 MiB for this workload. These were chosen against the measured M2 baseline, not as consumer requirements. The evidence publishes exact observed values and a 64 MiB guest test. The bitmap metadata and bounded tables reside inside the separately counted kernel image.

The bootloader sizes its map buffer from firmware plus descriptor slack in M2 rather than retaining M1's fixed 256 KiB buffer. Framebuffer fills use direct rows instead of a bounds/color function for every pixel. No service/thread is started speculatively.

Idle verification checks QEMU's actual `HLT=1` register state and samples QEMU process CPU time over a reported two-second wall interval, with a generous 15% of one host CPU ceiling to catch polling. This tiny halted demo is not a real-hardware, desktop or power benchmark. General memory/scheduling/pressure optimization continues in M3.

## Windows 95–11 and next milestone

[WC1–WC7](../roadmap/windows-compatibility.md) remains the product requirement: Win16/NE, PE32/PE32+, 9x/NT semantics, runtimes/installers, multimedia and driver/service dependencies. Native entry, handles and memory are designed to host adapters later. No existing Windows application has been installed or run, and the third-party register remains empty.

M3 adds interrupt-driven preemption, threads, waiting/deadlines, general VM/pressure and concurrency. Persistent storage/input is M4; actual OS installation is M5. See [detailed roadmap](../roadmap/milestones.md).

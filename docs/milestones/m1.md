# M1 — original own-kernel boot

M1 delivered an original x86-64 UEFI loader → ExitBootServices → ELF64 kernel, with no Windows/Linux/FreeBSD kernel underneath. This is a completed historical milestone; [M2](m2.md) is the latest development image. There is no installer yet.

## Run the M1 path

[Historical M1 prerelease](https://github.com/enginsoysal/engacer-os/releases/tag/m1-v0.1.0), [evidence](../../evidence/M1/README.md).

```powershell
python tools/build/m1.py
python tools/vm/run.py --milestone M1 --ram 512
```

A current-source rebuild can have a different build ID from the immutable historical release; its published checksums identify the original files. Put a downloaded ISO at `dist/EngineOS-M1.iso` to use the launcher without rebuilding. It displays the boot screen and halts, with no keyboard handling, shell, app loader or installation UI. Close the VM window to stop. `--usb`, `--headless`, `--debug` and `--qemu-dir` are available; debug pauses at startup and binds GDB to loopback port 1234.

## Artifacts and reference platform

Normal ISO, GPT/FAT32 USB image, ELF/DWARF kernel, sanitized link map, build manifest and SHA-256 list. QEMU/OVMF are external dependencies, not bundled into the image. Qualification used pinned QEMU pc-q35-11.1/TCG, x64 OVMF, unsigned UEFI, normally 512 MiB/two configured vCPUs, with a 128 MiB case. A later user screenshot confirmed one VMware boot under a FreeBSD 15 64-bit VM profile; the profile did not provide a FreeBSD kernel. Physical/other-hypervisor qualification remains open.

## Implementation and rationale

- Original minimal public UEFI declarations plus layout/signature/CRC checks keep the loader bounded. Firmware opens boot files; that is not a kernel filesystem driver.
- Restricted ET_EXEC/x64 ELF segments from 2 MiB reject wrong architecture, dynamic binaries, overflow, RWX and overlapping pages; this does not provide Linux compatibility.
- Recorded allocations and boot-header/map checks preserve ownership. Loader memory is not reclaimed prematurely.
- Initial own low-4-GiB identity tables make transition diagnostics simple. They are broadly supervisor RWX with a present null page in M1; M2 replaces them before user entry. This is not the final security/physical-memory architecture.
- Bounded final-map/ExitBootServices retry and an explicit MS-x64→System-V transition eliminate firmware-service dependencies after handoff.
- Own GDT/TSS, 256 IDT entries and double-fault IST support diagnostics. A genuine `ud2` produces vector/error/RIP/CR2 and maps to `kernel_fault_probe`/source line; not every exception was forced.
- The kernel draws an original uppercase bitmap font through GOP's retained framebuffer, with CPU stores rather than firmware console or GPU acceleration.
- Fixed 48-byte manifest binds mode/build. Normal mode 0 persists; test modes 1–4 exit, panic, corrupt the header or inject a stale mapkey. They are not Secure Boot authentication.

Original acceptance: 19 C ELF-parser checks, seven boot/error scenarios, three persistent-screen/debugger checks, plus all 51 M0 regressions. Historical results are tied to their manifest/tag; M2 has separate current reports. `python tests/m1/verify.py` rebuilds/tests the current-source M1 path and may refresh those local reports.

## Product boundaries

Windows 95–11 remains the explicit [future compatibility requirement](../roadmap/windows-compatibility.md). M1 implemented no existing Windows application, syscall decoder or installer. M2 adds protected native probes; storage/input and a real installer remain M4/M5. [Architecture](../architecture/overview.md).

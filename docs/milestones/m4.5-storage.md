# M4.5 storage and trust increments

M4.5 remains **in progress**. This increment is not the whole [agreed milestone](m4.5.md).

## What changes from M4

The M45 build discovers ordinary SATA/AHCI devices without an Engine OS marker or a fixed capacity. It reads IDENTIFY capacity and logical sector size, owns reset/link/FIS initialization and enumerates multiple ports/controllers. First-sector transfer is checked before reporting a readable device. The registry distinguishes discovery/capability, actual read errors and explicit development-volume write authorization. Four AHCI controllers and sixteen storage devices bound state/DMA allocation. Discovery switches ports only after stopping the previous receive/command engines; uncertain DMA ownership quarantines the controller.

An original read-only NVMe driver owns controller enable/disable, 16-entry admin and I/O queues, Identify controller/active namespaces, namespace geometry, PRP DMA and MSI-X/MSI completion with HLT waits. A bounded polling fallback is explicit. Up to two controllers and sixteen namespaces are represented. The tested QEMU profiles have 512-byte and 4096-byte logical sectors. AHCI 4-KiB logical-sector parsing is not physical qualification: the pinned QEMU IDE model rejects that configuration, so native 4-KiB transfer tests use NVMe. NVMe timeout/error paths retain DMA pages, not memory potentially still owned by hardware.

The second increment adds original read-only ATA/PIO and modern VirtIO block transports. ATA binds PCI IDE compatibility/native I/O channels, uses bounded IDENTIFY and PIO sector reads and does not allocate DMA buffers; this is an explicit polling compatibility fallback, not the efficient default. Modern VirtIO negotiates the version-1 split-queue interface, uses eight descriptors with one three-descriptor request outstanding, and retains a 4-KiB queue, header/status page and 4-KiB data page per device. MSI-X completion sleeps with HLT and a timed wake backstop; a bounded polling fallback is explicit. Up to two VirtIO devices have separate supervisor MMIO mappings. Device protocol IDs identify VirtIO transport rather than a brand/model driver list. No VirtIO write feature is offered. Native tests read real MBR/GPT signatures and allocation metadata through these transports, including 512/4096-byte VirtIO sectors and repeated queue wrap; backing hashes must remain unchanged.

Ordinary disks remain read-only in our kernel. Only the separately validated, marked M4 development volume can use its existing ext2 write API; inspection of other devices must restore that selection before any later write. A mixed four-disk test verifies ordinary backing-file hashes remain unchanged while native ext2 tests deliberately modify the marked disk.

## Partition and filesystem reads

The original partition reader validates primary/backup GPT headers, header/table CRCs, usable ranges and overlapping partitions. The initial allowlist bounds GPT to 128 entries with power-of-two entry sizes between 128 bytes and the device sector size. MBR primary entries are range/overlap checked; extended/hybrid layouts are explicitly unsupported. Missing tables are reported separately from unreadable devices. NTFS/exFAT signatures are recognized but are not mounted or writable.

The original read-only FAT32 reader validates BPB geometry, sector/cluster/FAT bounds, mirrored allocation entries and bounded cluster chains. It reads short names and checksum-linked UTF-16 long names, including surrogate handling and UTF-8 conversion. Requested dot/dot-dot paths cannot escape the root. ASCII lookup is case-insensitive; full Unicode case folding is not claimed. Directory walks are capped at 128 clusters; console file reads are capped at 4 KiB. Unknown metadata, bad chains/mirrors or unsupported geometry fail explicitly. This is not FAT12/FAT16/exFAT/NTFS implementation.

Commands in the M45 console: `disks`, `hardware`, `parts N`, `fatls N P`, `fatcat N P /PATH`. Existing development-file commands remain available when a marked ext2 volume is mounted. `ls` without an argument now means the native root. PCI inventory distinguishes a storage controller with verified transfer from an unbound/unsupported candidate; network driver support remains later work.

```powershell
python tools/build/m45.py
python tools/vm/run.py --milestone M45 --data-disk build/m45/example.img
python tests/m45/storage.py
python tests/m45/fat32.py
```

The M45 launcher accepts only regular sector-aligned disposable raw images and uses a temporary QEMU snapshot overlay. This preserves the backing image even if firmware changes it before the kernel starts. Tests that assert kernel non-modification use explicitly owned disposable files and compare full hashes. OVMF can repair a damaged primary GPT from its backup before kernel entry; the negative fixture therefore corrupts both headers so that our kernel actually sees the error.

## Owner-key Secure Boot test chain

`python tests/m45/sha256.py` executes the exact freestanding C SHA-256 through a no-CRT host DLL and checks known/boundary vectors against independent hashes. The separately built verified EFI loader contains SHA-256 digests of the exact kernel and init payload. Firmware authenticates the signed PE loader; the loader authenticates both external payloads before ELF loading/ExitBootServices. A valid CRC alone is not a trust check.

`python tests/m45/secure_boot.py` generates an ephemeral VM test owner certificate, signs using the pinned Windows SDK SignTool, and enrolls db/KEK/PK only into disposable QEMU NVRAM. The test-only helper refuses non-TCG execution, non-SetupMode policy and nonempty existing key databases. PK enrollment supplies a proof-of-possession signed authenticated-variable update. Neither private PFX nor enrollment media is a release asset. Test tooling/secure firmware hashes are recorded in [the security tool lock](../../tools/security-toolchain.json); these are local observed pins, not independent upstream-authenticity proof.

The owner-key route is distinct from factory Microsoft/OEM trust. The normal development ISO remains unsigned; it must not be advertised as Secure-Boot-ready. Signed test media are generated locally under ignored build output. A production owner-key signing/enrollment/update policy and physical/factory-trust qualification remain open. No host firmware, global certificate store or existing VM is modified.

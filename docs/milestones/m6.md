# M6 — real product installation

Status: **in progress; no M6 ISO or completed runtime acceptance**. [Owner acceptance contract](../roadmap/milestones.md).

## Delivery slices

1. Capacity/accounting and target planning: deterministic freestanding C geometry, checked boundaries, exact partition review. The initial planner is implemented and host-tested; it performs no disk writes and is not yet connected to the installer.
2. Scalable storage: replace the fixed single-group 16-MiB filesystem and direct-only 48-KiB file path; add bounded streaming I/O, integrity validation and usable capacity reporting. Large files must survive detached repeated boots. This remains unimplemented.
3. Install and first-run setup: consume the validated plan, format and verify supported targets, place independently bootable system assets and persist the user's settings/account and native root directories. Preserve guided review/cancel and revalidate target identity. This remains unimplemented for M6.
4. Updates and recovery: copy an inactive system slot, verify it, activate through a redundant generation/checksum record, and retain the previous verified slot. Boot failure and interrupted transitions must have tested recovery. Slot geometry alone does not implement rollback. This remains unimplemented.
5. Qualification and release: disposable VMware BIOS/UEFI SATA targets and ISO/USB media, refusal/cancellation/disk identity, failed writes and activation interruptions, persistence, resource measurements, current English guides and exact release ISO hashes. This remains unimplemented for M6.

## Initial partition decision

The initial supported install target is a new SATA/AHCI disk with 512-byte logical sectors, from 2 GiB through 2 TiB. Wider hardware support requires separate implementation and evidence. Geometry reserves a protective MBR/primary GPT, a 4-MiB BIOS boot partition, a 128-MiB EFI partition, two 512-MiB native system slots, a data partition using all remaining aligned capacity, and the backup GPT. Leading/trailing alignment and GPT sectors are explicitly accounted for. Existing partitions are not overwritten by a planner; the destructive installer must still validate ownership and confirmation.

**Why:** separate boot assets and two bounded system slots prepare a recoverable update path without copying a complete user volume. Applications and durable user data belong in the scalable data volume; system slots hold the bootable base. 512 MiB per slot is an initial budget to validate against the actual base image, not a claim that any future image fits. Images that exceed it must be refused or the layout version revised. The previous fixed demonstration data partition cannot serve useful downloads or applications.

The planner allocates no heap, touches no hardware and runs in constant space/time. It refuses unsupported sector sizes/capacities and leaves the output untouched on refusal. It is shared C suitable for the freestanding kernel rather than a Python-only partition simulation. Host execution proves arithmetic and refusal behavior, not actual formatting, installation, crash recovery or filesystem capacity.

## First slice verification

Run `python tests/m6/layout.py`. It compiles the actual planner for both the freestanding kernel target and a host-test DLL with the pinned compiler, then checks exact capacity accounting, aligned non-overlapping partitions, GPT boundaries, minimum/maximum/odd-sized disks and refusal behavior. New evidence is under `evidence/M6`; accepted M0–M5.1 reports and released artifacts remain unchanged.

## User-visible result

The released M5.1 ISO remains the current downloadable prototype. This first M6 slice changes no boot screen. A new M6 ISO will be published only after its installer/storage integration and runtime checks; the graphical desktop is the next milestone, M7. Engine OS remains the product name.
